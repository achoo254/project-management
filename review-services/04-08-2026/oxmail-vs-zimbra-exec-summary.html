§0 Mở đầu

Vấn đề cần giải quyết: tại sao xây lại hạ tầng mail năm 2026?

Stack legacy gánh quá nhiều lớp từ thuở email còn là giao thức thuần văn bản. Mỗi lớp là một rủi ro vận hành, một nợ bảo mật, một khoản chi phí.

Đau đớn từ stack cũ

  • Zimbra ~80+ tiến trình, Postfix + Dovecot + Amavis + SpamAssassin = 6+ services, nhiều runtime và mô hình quản lý bộ nhớ khác nhau (Python, Perl, C, Lua) làm tăng độ phức tạp vận hành và debug, upgrade path phức tạp
  • Gánh nặng vận hành: schema migrations qua 3 DB, LDAP replication, shared storage (NFS/GlusterFS), đội ops 24/7 cho failover
  • Nợ kỹ thuật bảo mật: DKIM/ARC/MTA-STS không phải first-class, tích hợp WebAuthn/FIDO2 cần code glue
  • Không phù hợp cloud-native: stateful workloads, không container-native design, secrets management phải ghép thêm
  • Chi phí TCO ẩn: license + hardware + ops + upgrades + security patches

Luận điểm của OxMail

  • Một mail server native Rust, single binary loại bỏ các layer này trong khi duy trì hoặc vượt qua capability parity
  • Một application binary, một domain model thống nhất, một event bus chính và một cấu hình ứng dụng trung tâm
  • Runtime zero-GC loại bỏ GC pause như một production concern (khác với JVM/Zimbra)
  • Memory safety không cần garbage collector: safe Rust giảm mạnh lớp lỗi memory corruption trong code ứng dụng, ngoại trừ vùng unsafe/FFI/dependency native
  • Đo trên production: app processes ~90-140 MB, 3 OS threads; toàn node stack ~2.4-3.3 GB (§9.6)

§2.6 Gateway (GW)

OxMail là first-class citizen của GW - kết nối gRPC + rkyv

GW (repo riêng, node 103.72.96.181) là gateway chia sẻ: MX tập trung, IP pool delivery, outbound routing theo domain. gateway.proto là contract chung, thay đổi RPC commit song song cả 2 repo.

Kết nối gRPC bidirectional stream

Stream A (Forward): GW → OxMail   inbound sau security pipeline
Stream B (Submit):  OxMail → GW   outbound cho IP pool delivery

RPC: Forward · Submit · Ping · ListDomains
     · GetDeliveryStatuses · RetryDeliveries

Payload: rkyv-serialized (GatewayMessageV1 / OutboundMessageV1)
         - rkyv::access cho zero-copy payload access sau khi nhận frame
           (không deserialize object graph mới)
  • gRPC + rkyv: zero-copy payload access ở tầng payload sau khi nhận frame; nhanh hơn SMTP forwarding truyền thống (vẫn hỗ trợ SMTP làm fallback)
  • Submit endpoint: 103.72.96.181:50052; OxMail nhận gateway trên 0.0.0.0:50053
  • Auth: bearer token (OXMAIL_GATEWAY_SUBMIT_TOKEN)

Vai trò trong kiến trúc

  • Forwarding dự phòng: vẫn hỗ trợ SMTP forwarding truyền thống

§2.10.5 Deep dive — DLP / ZAP / Gray-zone

Ba lớp phòng thủ AI — lợi thế duy nhất OxMail đang xử lý

Zimbra dựa vào Amavis (inline, binary, không AI). OxMail có 3 worker AI độc lập chạy nền qua NATS — không chặn đường deliver chính, retry tự động, có circuit breaker. Đây là nhóm tính năng khó copy nhất: cần pipeline đúng chỗ, AI provider đúng chuẩn, và dữ liệu vận hành thật.

Gray-zone — AI Courtlợi thế khó copy nhất

Vai trò: toà án AI cho vùng mail lấp lửng (score 5–7) — nơi threshold cứng của Zimbra/Postfix hoặc chặn nhầm (false positive mất thư quan trọng) hoặc thả lọt (spam lừa đảo tinh vi). Gray-zone giữ mail, hỏi AI, rồi mới quyết định — không bao giờ 554 ở tầng này.

SMTP pipeline (score trong [5, threshold] và ai.enabled)
  ├─ hold(): lưu raw vào S3 (blob) + insert gray_zone_review (pending)
  ├─ publish NATS "mail.gray_zone.review"
  └─ trả 250 "held for review" (sender thấy đã nhận)

oxmail-gray-worker (consumer max 10 concurrency)
  ├─ 1. dedup cache (Dragonfly, 24h TTL theo message_id_hash)
  ├─ 2. reputation gate: ≥3 user report cùng sender → auto-junk, KHÔNG gọi LLM
  ├─ 3. rate limit (max_calls_per_minute, Dragonfly INCR+EXPIRE)
  ├─ 4. resolve judge theo tenant (Dragonfly key, system/tenant scope)
  ├─ 5. LLM Judge — prompt có phòng thủ chống prompt-injection:
  │     • body trong <email_body> = untrusted input, bỏ qua lệnh nhúng
  │     • đánh giá: domain drift (display name ≠ envelope domain),
  │       urgency tone, đối chiếu spam_symbols + điểm rspamd
  ├─ 6. verdict: DELIVER → INBOX / JUNK → Junk
  │     HOLD (không chắc) → xử lý như JUNK (fallback an toàn)
  │     LLM lỗi/timeout/circuit mở → auto-JUNK
  └─ 7. ghi ai_verdict/ai_reason/ai_model + inject message vào mailbox
        + publish "mail.gray_zone.verdict" (NATS)

Watchdog (trong oxmail-server, mỗi 30s):
  pending quá 300s → force ai_verdict='junk', actor='system-watchdog'
  → mail vào Junk, không bao giờ kẹt vô thời hạn
  • Vì sao lợi thế: (1) Zimbra không có khái niệm "vùng xám + AI xét" — Amavis chỉ phân loại cứng; (2) cần dữ liệu thật để tinh prompt (domain drift, urgency); (3) per-tenant AI provider (domain admin cấu hình riêng, key riêng) — mô hình MSP bán được; (4) watchdog đảm bảo không chết im lặng.
  • Chi phí: chỉ gọi LLM cho mail score 5–7 (phần nhỏ traffic) — không quét toàn bộ.
  • Verify production: phish (bank + bit.ly) → verdict junk "Generic bank-suspension threat..."; mail sạch → AI HOLD → junk fallback (bảo thủ có chủ đích).

DLP — Data Loss Prevention

Vai trò: ngăn rò rỉ dữ liệu outbound — số thẻ, IBAN, SSN, secret/API key, JWT, custom regex/keyword. Quét mọi thư rời hệ thống (JMAP lẫn SMTP AUTH).

Enqueue (JMAP + SMTP submission)
  → publish "mail.outbound.dlp_check"
oxmail-dlp-worker:
  1. pattern engine (regex pre-compiled:
     PCI_CARD, IBAN, US_SSN, PLAINTEXT_SECRET,
     JWT_TOKEN, CUSTOM_KEYWORD, VN_*)
  2. AI judge per-policy (use_llm + provider/model):
     schema {has_sensitive_data, findings, risk_level}
     high/critical → block · medium → quarantine
     false → allow (overrule regex nếu nhầm)
  3. ghi verdict: dlp_status + dlp_reason + dlp_verdicts
Verdict: allow → GW/direct deliver
         block → 550 5.7.1 (delivery trace + nút Retry)
         quarantine → DLP quarantine, admin review
  • Retry chủ ý: khách hàng biết mình gửi gì → bấm Retry trong delivery trace → override dlp_status='allow' + ghi ai override, không quét lại.
  • Role trong log: scan log hiện đầy đủ mọi verdict + AI Role (system = root provider / tenant = domain admin).
  • Bug đã vá khi verify: schema LLM sai (parse luôn allow) + SMTP submission bỏ qua DLP — cả 2 đã fix + verify block thật 550.

ZAP — Zero Auto Purge

Vai trò: retro-scan attachment sau khi ClamAV cập nhật signature — mail cũ tưởng sạch, giờ mới phát hiện virus. "Bom hẹn giờ" của Zimbra: không có cơ chế này.

Trigger (3 đường):
  1. Freshclam OnUpdateExecute
     → POST /internal/zap/trigger (HMAC, chống replay)
  2. Admin UI 9443 (nút Trigger Scan)
  3. Crowdsourced: 3 user report cùng sender
     → scan mail 7 ngày của sender đó

Trigger → query attachment blobs (window 6h)
  dedup: skip blob đã scan từ lần trigger trước

7.1 · TLS connection pool (outbound SMTP) — oxmail-smtp-outbound/src/pool.rs

Cách làm bình thường (Postfix / Zimbra)

  • Mỗi message (hoặc mỗi đợt) mở kết nối TCP mới → EHLO → STARTTLS → TLS handshake đầy đủ: 2 RTT (ClientHello → ServerHello/KeyShare → Finished) + verify chứng thư + sinh khóa phiên.
  • Zimbra: mỗi delivery worker tạo connection riêng, không tái sử dụng qua message; Postfix có sender_dependent nhưng per-connection TLS state thường reset.
  • Kết quả: với MX lớn (gmail/outlook), phần lớn thời gian delivery là handshake, không phải gửi thư; đồng thời dễ mở quá nhiều kết nối đồng thời tới 1 MX (bị rate-limit/đánh dấu spam).

Tại sao OxMail chọn pool + session resume

  • TlsConnectionPool lưu kết nối đã handshake theo (MX host, port); NOOP health-check trước khi tái dùng (MX hay đóng kết nối im lặng — dùng lại là hỏng).
  • Session ticket cache (TlsSessionCache): sau mỗi handshake lưu ticket → lần sau TLS 1.3 PSK resumption (~1 RTT, bỏ verify chứng thư, dùng khóa phiên cũ).
  • Per-MX semaphore (max_per_mx): serialize số kết nối tới 1 MX — chống thundering herd, không bị MX chặn vì quá nhiều conn.
  • Background cleanup idle TTL (mỗi idle_ttl/2 giây) + pre-warm MX phổ biến (gmail, outlook) ngay khi khởi động.

7.2 · jemalloc — global allocator (zero-GC) — oxmail-server/main.rs (static GLOBAL: Jemalloc)

Cách làm bình thường (glibc malloc / mimalloc)

  • glibc malloc (mặc định): per-thread arenas, nhưng không có chiến lược chunk reuse cho workload long-lived connections — mỗi connection giữ buffer/heap riêng; freed chunk bị fragment nhỏ dần → RSS tăng theo thời gian.
  • mimalloc: RAM tốt hơn, nhưng có cleaner thread định kỳ — có thể tạo latency spike ở thời điểm không lường trước.
  • Java (Zimbra): GC pause dưới heap lớn — tail latency nhảy ms → chục ms; phải tinh chỉnh JVM flags.

Tại sao OxMail chọn jemalloc

  • Triết lý zero-GC: mail server giữ kết nối rất lâu (IMAP IDLE hàng giờ/ngày, SMTP connection reuse). Cần allocator cho tail latency dưới ms, ổn định, không pause.
  • jemalloc: arenas (mỗi thread tốc độ cao có arena riêng — không lock contention) + chunk reuse (freed chunk trả về pool tái dùng cùng kích thước) → fragmentation tối thiểu, RSS ổn định.
  • Không có background thread định kỳ "dọn" — không latency spike ẩn.
  • Số liệu production (node ox.io.vn): uptime 54 ngày, load 0.30, memory ổn định không leo — phù hợp giả định jemalloc chống fragmentation.

7.3 · Bumpalo arena — zero-alloc protocol response — oxmail-common/src/bump_writer.rs

Cách làm bình thường (String/Vec mỗi response)

  • Mỗi lệnh SMTP/IMAP trả 1 response. Cách thông thường: build bằng String/Vec<u8> — mỗi lần push_str/write! có thể cấp phát lại heap (amortized nhưng vẫn nhiều allocation), mỗi field riêng một allocation, rồi từng cái free riêng.
  • Với hàng nghìn lệnh/phút/connection → allocation churn: syscall + fragmentation nhỏ dần, cache locality kém.
  • IMAP list response lớn (LIST 1000 mailbox) → hàng trăm allocation cho 1 response.

Tại sao OxMail chọn bumpalo arena

  • BumpWriter bọc bumpalo::collections::String trong một bumpalo::Bump arena mỗi lệnh: mọi buffer con được bump (tăng con trỏ — vài instruction, không syscall), không free từng cái.
  • Cuối lệnh: into_string() copy 1 lần ra heap rồi drop(arena) — 1 lần free toàn bộ.
  • Arena !Send → phải tiêu thụ xong trong scope connection (đúng mô hình request/response SMTP/IMAP).
  • Đang dùng ở IMAP (auth, extensions, message fetch, LIST) + SMTP response path.

§11 Roadmap

Ngắn hạn (Q3-Q4 2026)

  • Production benchmarks (số thật, không lý thuyết)
  • Full SMTP AUTH (PLAIN/LOGIN credential handling)

  • Groupware: Tasks, Notes (JMAP)

Dài hạn

  • Tự viết engine chống spam/virus thay Rspamd + ClamAV, kết hợp học máy (AI/LLM) ngay trong pipeline; bỏ phụ thuộc binary external, mở rộng gray-zone AI. Động lực đo được: ClamAV chiếm 0.97-1.95 GB RAM/node - kẻ ngốn lớn nhất node (§9.6)
  • Multi-region replication (CRDT conflict resolution)
  • Hardware security module (HSM) cho KEK
  • Fediverse / SMTP-over-TOR integration
