Tóm tắt buổi học

Buổi 1 dạy gì?

Buổi học đi từ nguyên lý (vì sao container ra đời, ưu điểm so với ảo hóa) đến thực hành tay trên một máy chủ Linux đã cài Docker — trọng tâm là vòng đời container và cách chứng minh "image là bất biến".

🎯
Mục tiêu Phần 1. Xây nền khái niệm + kỹ năng thao tác cơ bản: cài đặt Docker, quản lý image, chạy & điều khiển vòng đời container, đọc log/sự kiện/tài nguyên. Chuẩn bị cho các buổi sau về Dockerfile, Docker Compose và Kubernetes.

✅ Sau buổi này bạn sẽ

  • Giải thích được container khác máy ảo ở đâu, vì sao nhẹ/nhanh hơn.
  • Cài Docker theo quy trình chuẩn có bước xác minh từng bước.
  • Pull/inspect/tag image, hiểu cơ chế chia sẻ layer.
  • Chạy container Nginx, điều khiển đủ vòng đời (stop/start/rename/exec/rm).
  • Tự chứng minh tính bất biến của image bằng thực nghiệm "sửa nóng".
  • Đọc log container vs log ứng dụng, theo dõi docker stats/docker events.

👥 Đối tượng & yêu cầu

Kỹ sư/DevOps Bộ phận Công nghệ. Một số đã dùng Docker cơ bản (mở port, chạy container có sẵn) nhưng chưa thực hành sâu vòng đời, log, registry.

Nguyên lý · Phần 1

Vì sao container ra đời?

Dòng tiến hóa hạ tầng CNTT

Giảng viên dẫn dắt ngược dòng lịch sử: "Trước Cloud là gì? — Ảo hóa. Trước ảo hóa? — Vật lý." Mỗi bước tiến giúp khai thác tài nguyên phần cứng tốt hơn.

  • ① Máy chủ vật lý

    Một máy = một mục đích. Hiệu suất khai thác CPU/RAM thấp, tốn điện, khó co giãn.

  • ② Ảo hóa (VMware, KVM, Hyper-V, Citrix)

    Chia một máy vật lý thành nhiều máy ảo → khai thác được 80–95% năng lực phần cứng, tiết kiệm điện.

  • ③ Cloud (OpenStack, CloudStack)

    Tự phục vụ, cấp phát tài nguyên theo yêu cầu, co giãn nhanh trên nền ảo hóa.

  • ④ Container (Docker, Kubernetes)

    Đóng gói ứng dụng ở mức nhẹ hơn máy ảo. Giảng viên gọi vui là "IaaS 1.5" — nằm giữa hạ tầng và nền tảng ứng dụng. Mật độ phục vụ cao hơn hẳn.

🚢
Ví von "container vận tải" (giảng viên nhấn mạnh). Thập niên 1960, hàng hóa quốc tế đóng gói tùy tiện (thùng, vải bọc…), không tiêu chuẩn → lãng phí diện tích trên ô tô/tàu thủy/tàu hỏa. Người ta phát minh container hàng hải (conex) — hộp tiêu chuẩn để đóng gói & vận chuyển thống nhất trên mọi phương tiện. Docker áp dụng đúng ý tưởng đó cho phần mềm: đóng gói ứng dụng theo chuẩn để chạy nhất quán từ máy dev → staging → production → cloud → tại chỗ khách hàng.

Bài toán cụ thể

😖 Không có container

  • Một máy vật lý khó chạy đồng thời nhiều môi trường (cài Java rồi khó cài PHP song song).
  • Chuyển ứng dụng giữa dev/staging/production phải setup lại từ đầu → "máy tôi chạy được mà".
  • 70–80% hệ điều hành cài đặt là phần dư thừa không dùng đến.

🙂 Có container

  • Đóng ứng dụng + thư viện vào "một thùng", chạy nhiều container trên cùng hạ tầng.
  • Mang "thùng" đi bất kỳ đâu, chạy nhất quán không lo nền tảng bên dưới.
  • Image tối giản — ví dụ image WordPress chạy được chỉ ~60MB (bỏ SSH server, phần dư…).

Container dùng chung kernel của host, bỏ được lớp guest OS → nhẹ, nhanh, nhỏ.

💡
Định nghĩa cốt lõi. Container về bản chất là một tiến trình (process) của host, không phải một máy ảo đầy đủ. Vì dùng chung kernel với host nên nó khởi động chỉ trong vài giây (không phải boot cả một OS) và chiếm rất ít tài nguyên.

Ba thành phần của Docker

🧠 Docker daemon (dockerd)

Tiến trình chạy nền trên Docker Host — quản lý image và chạy container.

🗄️ Registry

Nơi chứa image: public (Docker Hub, quay.io…) hoặc registry riêng tự dựng (Harbor, Nexus, registry:2).

⌨️ Docker CLI

docker build, docker pull, docker run… — công cụ ra lệnh cho daemon.

🔀
Đọc sơ đồ kiến trúc phải để ý nét vẽ. Đường liền nét = luồng docker pull (kéo image có sẵn về); đường nét đứt = luồng docker build (build image từ Dockerfile). Thực tế đa số là pull, chỉ khi cần tùy biến mới build.

Image, Layer & cơ chế lõi Linux

🧱 Image & Layer — vì sao dung lượng nhỏ bất ngờ

Mỗi lần đóng gói lại ứng dụng (thêm tính năng/sửa code) tạo ra một layer mới kế thừa layer trước — giống quản lý version. Các image khác nhau chia sẻ chung layer giống nhau. Ví dụ kéo Python 3.11 + 3.12: tưởng phải ~4.5GB nhưng thực tế chỉ ~1.7GB vì dùng chung phần lớn layer nền.

🧩 Namespace + cgroups — công nghệ "không hề mới"

Namespace cô lập không gian tài nguyên (network, PID, mount…). cgroups (control groups) giới hạn/chia CPU, RAM cho từng nhóm tiến trình. Union filesystem hiện thực cơ chế layer.

Các cơ chế này đã có trong Linux kernel hàng chục năm. Câu chuyện giảng viên kể: cgroup ra đời từ bài toán một máy 64 core nhưng phần mềm cũ chỉ xài được 8 core → lãng phí đầu tư → kỹ sư nghĩ ra cách "chia nhỏ CPU" cho nhiều tiến trình. Docker chỉ đóng gói các cơ chế này thành CLI dễ dùng, không phát minh ra khái niệm cô lập tiến trình.

🧭 Compose · Swarm · Kubernetes (giới thiệu, học sau)
  • Docker Compose — gộp nhiều container (web + DB + cache…) vào một file docker-compose.yml, chạy một lệnh khởi động cả hệ.
  • Docker Swarm — điều phối container trên nhiều máy; nay ít dùng, xu hướng chuyển sang K8s.
  • Kubernetes (K8s) — lớp trừu tượng điều phối container quy mô lớn. Học ở buổi sau.
📐
Chuẩn mở giúp tương thích. Docker, Podman, containerd… tuân theo một chuẩn chung (OCI — Open Container Initiative) nên image/registry của các nhà cung cấp khác nhau vẫn dùng qua lại được. Container chỉ phụ thuộc kernel bên dưới, không phụ thuộc distro cụ thể (khác package Linux: Ubuntu repo ≠ RedHat repo).
Ghi chú biên soạn: transcript nghe không rõ tên chuẩn; suy luận theo ngữ cảnh là OCI.

Khái niệm quan trọng nhất buổi

Tính bất biến & dữ liệu

◆ Hai định nghĩa phải nhớ

  • Image là bất biến (immutable). Mỗi lần chạy là chạy đúng phiên bản image tại thời điểm tạo. Muốn thay đổi lâu dài phải thay thế bằng image mới (sửa nguồn → build lại), không sửa tại chỗ.
  • Container không lưu state. Docker chỉ là môi trường chạy. Dữ liệu phải ghi ra ngoài host qua volume — nếu không, xóa container là mất dữ liệu.
🔥
"Sửa nóng" chỉ là phích tạm — KHÔNG phải cách làm đúng. Bạn có thể exec vào container sửa trực tiếp file (ví dụ trang index.html của Nginx) và thấy web đổi ngay. Nhưng khi xóa container rồi tạo lại từ cùng image, mọi thay đổi biến mất — web trở về mặc định. Đây là bằng chứng trực quan cho tính bất biến. Xem Lab 4 để tự làm.
🗂️
Đừng nhồi mọi thứ vào container. Quan điểm "cho hết code + data vào trong container" là sai lầm thiết kế. Container chỉ nên chứa runtime; code/data nên mount ra ngoài qua volume để dễ cập nhật, sao lưu mà không đụng tới container.
Lab về volume sẽ có ở Phần sau — xem lộ trình trong mục Labs.

LAB 01

Cài đặt Docker & kiểm tra môi trường

⏱ 20–25′ Độ khó

Mục tiêu: cài Docker Engine trên Linux theo quy trình có xác minh, và đọc được thông tin môi trường trước/sau khi cài.

  1. Kiểm tra thông tin máy trước khi cài
    bash
    ip a                 # IP của máy
hostnamectl          # hostname, OS, kernel
cat /etc/os-release  # distro & version
    ✔

    Kiểm chứng: xác định đúng distro (Ubuntu/Debian/RHEL…) và kernel ≥ 3.10 để chọn đúng lệnh cài.

  2. Cài Docker Engine từ repo chính thức (ví dụ Ubuntu/Debian — quy trình 8 bước rút gọn)
    bash
    sudo apt update
# cài script tiện lợi (lab); production nên cài theo repo + GPG key thủ công
curl -fsSL https://get.docker.com | sudo sh
    ✔

    Kiểm chứng: lệnh chạy xong không báo lỗi; chuyển bước xác minh version.

  3. Kiểm tra version & dịch vụ
    bash
    docker version
docker compose version
sudo systemctl enable --now docker   # start + bật khi reboot
systemctl status docker --no-pager
    ✔

    Kiểm chứng: thấy cả Client và Server version; service active (running).

  4. Chạy Docker không cần sudo (thêm user vào group docker)
    bash
    sudo usermod -aG docker $USER
# đăng xuất/đăng nhập lại (hoặc: newgrp docker) để áp dụng
docker info
    ✔

    Kiểm chứng: docker info chạy được không cần sudo. Quan sát: Docker đã tạo network bridge mặc định; ghi nhớ Docker Root Dir = /var/lib/docker.

💾
Lưu ý vận hành: /var/lib/docker sẽ phình to theo thời gian (image/layer/log). Nên đặt nó trên phân vùng/đĩa dung lượng lớn ngay từ đầu.
LAB 02

Quản lý image: pull · inspect · tag · layer sharing

⏱ 15–20′ Độ khó

Mục tiêu: làm chủ vòng đời image và quan sát cơ chế chia sẻ layer giữa các version.

  1. Container test đầu tiên
    bash
    docker run --rm hello-world
docker image ls
    ✔

    Kiểm chứng: thấy thông báo "Hello from Docker!"; image hello-world < 1MB. Docker tự pull vì local chưa có.

  2. Pull nhiều version & quan sát chia sẻ layer
    bash
    docker pull python:3.11
docker pull python:3.12
docker image ls | grep python
    ✔

    Kiểm chứng: tổng dung lượng đĩa thực tế nhỏ hơn tổng SIZE của từng image cộng lại — vì các layer nền được dùng chung.

  3. Inspect có lọc field + xem lịch sử layer
    bash
    docker image inspect --format '{{.Os}} {{.Architecture}}' python:3.11
docker image history python:3.11
    ✔

    Kiểm chứng: lệnh format in ra đúng 1 dòng (vd linux amd64) thay vì cả khối JSON.

  4. Tag theo naming nội bộ & dọn dẹp
    bash
    docker image tag python:3.11 lab.inet/python:3.11
docker image ls | grep lab.inet
docker image rm lab.inet/python:3.11   # xóa tag vừa tạo
    ✔

    Kiểm chứng: tag mới xuất hiện rồi biến mất sau khi rm; image gốc python:3.11 vẫn còn (tag chỉ là "tên gọi").

LAB 03

Chạy Nginx & điều khiển vòng đời container

⏱ 25–30′ Độ khó

Mục tiêu: chạy một web server thật và đi hết vòng đời "sinh ra → chạy → mất đi" của container.

  1. Chạy container Nginx
    bash
    docker run -d --name web --hostname web --restart always -p 8080:80 nginx
docker container ls
docker container port web
    ✔

    Kiểm chứng: mở http://<ip-server>:8080 trên trình duyệt máy khác → thấy trang "Welcome to nginx!".

  2. Hiểu binding port
    bash
    # -p 8080:80         -> public ra mọi interface (0.0.0.0), máy khác truy cập được
# -p 127.0.0.1:8080:80 -> chỉ truy cập được từ chính máy host (localhost)
curl -s http://localhost:8080 | head -n 5
    ✔

    Kiểm chứng: giải thích được vì sao bỏ IP thì truy cập được từ ngoài, còn gắn 127.0.0.1 thì không.

  3. Vòng đời: stop → start → pause → rename
    bash
    docker container stop web
docker container ls -a          # trạng thái Exited
docker container start web
docker container pause web      # web "sống" nhưng không phản hồi request
docker container unpause web
docker container rename web web-1
    ✔

    Kiểm chứng: sau stop web không truy cập được; sau start truy cập lại được; lúc pause trình duyệt bị treo chờ; sau rename container vẫn chạy với tên mới.

  4. Nhìn vào bên trong container
    bash
    docker container top web-1                 # tiến trình bên trong (nhìn từ host)
docker container exec -it web-1 /bin/sh    # chui vào trong
# --- bên trong container ---
hostname
ip a
ls /
exit
    ✔

    Kiểm chứng: top chỉ thấy tiến trình nginx (không thấy systemd của host → cô lập namespace); bên trong hostname/ip a khác host; ls / thấy filesystem tối giản.

LAB 04

Sửa nóng & minh chứng "image là bất biến" ⭐

⏱ 15–20′ Độ khó

Mục tiêu: lab "aha!" của buổi học — tự tay chứng minh container không lưu state và image bất biến.

  1. Sửa nóng trang chủ Nginx
    bash
    docker container exec -it web-1 /bin/sh
# --- bên trong container ---
cd /usr/share/nginx/html
echo "<h1>Xin chao tu iNET - da sua nong</h1>" > index.html
exit
    ✔

    Kiểm chứng: reload http://<ip-server>:8080 → thấy nội dung mới ngay lập tức.

  2. Xóa hẳn container vừa sửa
    bash
    docker container stop web-1
docker container rm web-1
    ✔

    Kiểm chứng: docker container ls -a không còn web-1.

  3. Tạo lại từ CÙNG image gốc (không build lại)
    bash
    docker run -d --name web --hostname web --restart always -p 8080:80 nginx
    ✔

    Kiểm chứng: reload trình duyệt → nội dung trở về "Welcome to nginx!" mặc định. Thay đổi "sửa nóng" đã biến mất hoàn toàn.

🧠
Rút ra: image bất biến; container không lưu state. Muốn đổi nội dung lâu dài phải sửa từ nguồn (Dockerfile — Phần 2) và build image mới, hoặc mount volume ra ngoài (Phần 4).
LAB 05

Inspect & log: container vs ứng dụng

⏱ 20–25′ Độ khó

Mục tiêu: đọc metadata container, phân biệt 2 loại log, và theo dõi log real-time dưới tải.

  1. Inspect có lọc field
    bash
    docker container inspect web
docker container inspect --format '{{.State.Status}}' web
docker container inspect --format '{{.HostConfig.RestartPolicy.Name}}' web
    ✔

    Kiểm chứng: lấy được đúng running và always mà không phải đọc cả JSON.

  2. Hai loại log
    bash
    # 1) Log CONTAINER (Docker capture stdout/stderr)
docker container logs --tail 20 web

# 2) Log ỨNG DỤNG (Nginx tự ghi, bên trong container)
docker container exec web ls -l /var/log/nginx
    ✔

    Kiểm chứng: phân biệt được: docker logs đọc stdout/stderr; còn /var/log/nginx/ là file log riêng của ứng dụng.

  3. Theo dõi log real-time dưới tải (2 terminal)
    bash
    # Terminal A — theo dõi
docker container logs -f web

# Terminal B — tạo 50 request có đánh số
for i in $(seq 1 50); do curl -s "http://<ip-server>:8080/?req=$i" > /dev/null; done
    ✔

    Kiểm chứng: Terminal A hiện đủ 50 dòng log tăng dần theo thời gian thực (đối chiếu tham số ?req=).

📡
Thực tế: đường dẫn log thô nằm ở /var/lib/docker/containers/<id>/<id>-json.log. Công cụ như Vector / VictoriaLogs tự nhận cấu trúc log Docker và thu thập tập trung — không cần mount thủ công.
LAB 06

Theo dõi tài nguyên & sự kiện

⏱ 15′ Độ khó

Mục tiêu: quan sát tài nguyên container và bắt sự kiện vòng đời real-time.

  1. Xem tài nguyên
    bash
    docker stats            # nhấn Ctrl+C để thoát
docker stats --no-stream # in một lần rồi thoát
    ✔

    Kiểm chứng: thấy cột CPU %, MEM USAGE / LIMIT của container web.

  2. Bắt sự kiện vòng đời (2 terminal)
    bash
    # Terminal A — theo dõi sự kiện của container web
docker events --filter container=web

# Terminal B — sinh sự kiện
docker container restart web
docker container stop web
docker container start web
    ✔

    Kiểm chứng: Terminal A lần lượt hiện restart, kill, stop, start đúng trình tự.

⚠️
Lưu ý: docker events không lưu lâu dài (chỉ giữ số sự kiện gần đây trong bộ nhớ). Container tự restart/stop bất thường là dấu hiệu ứng dụng có vấn đề — nên có giám sát (Vector/VictoriaLogs) để cảnh báo.

NHÓM PHẦN 1

Nền tảng & Vòng đời

10 bài
LÝ THUYẾT

1. Container khác máy ảo ở điểm cốt lõi nào khiến nó nhẹ và nhanh hơn?

Đáp án gợi ý

Container dùng chung kernel/OS với host, không cần guest OS riêng như máy ảo. Nó thực chất là một tiến trình của host được cô lập bằng namespace/cgroups → khởi động trong vài giây, tốn ít tài nguyên. Máy ảo phải qua Hypervisor và boot cả một guest OS đầy đủ.

LÝ THUYẾT

2. "Image là bất biến" nghĩa là gì? Nếu cần đổi nội dung ứng dụng lâu dài thì làm đúng cách như thế nào?

Đáp án gợi ý

Mỗi lần chạy là chạy đúng phiên bản image tại thời điểm tạo; không sửa nội dung bên trong theo cách bền vững. Cách đúng: sửa từ nguồn (Dockerfile/mã nguồn) rồi build image mới và thay thế container — chứ không exec vào sửa tay. Dữ liệu cần giữ thì đưa ra volume.

LÝ THUYẾT

3. namespace và cgroups khác nhau ra sao? Vì sao nói "container không phải công nghệ mới"?

Đáp án gợi ý

namespace = cô lập không gian nhìn thấy (PID, network, mount…); cgroups = giới hạn/chia tài nguyên (CPU, RAM). Cả hai đã có trong Linux kernel hàng chục năm (cgroup ra đời từ bài toán tận dụng CPU nhiều core). Docker chỉ đóng gói các cơ chế này thành CLI dễ dùng.

LÝ THUYẾT

4. Phân biệt "log container" và "log ứng dụng". Cho ví dụ với Nginx.

Đáp án gợi ý

Log container = stdout/stderr của tiến trình chính, xem bằng docker container logs. Log ứng dụng = file do chính app ghi, ví dụ Nginx ghi /var/log/nginx/access.log & error.log bên trong container. Hai nguồn độc lập, phục vụ mục đích khác nhau.

THỰC HÀNH

5. Chạy một container Redis tên cache ở chế độ nền, chỉ cho truy cập từ localhost qua port 6380, rồi kiểm tra nó đang chạy.

Đáp án gợi ý
bash
docker run -d --name cache -p 127.0.0.1:6380:6379 redis
docker container ls
docker container port cache

Gắn 127.0.0.1 để chỉ bind vào loopback → máy ngoài không truy cập được.

THỰC HÀNH

6. Chỉ dùng --format, lấy ra địa chỉ IP nội bộ của container web (không đọc cả JSON).

Đáp án gợi ý
bash
docker container inspect \
  --format '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}' web
THỰC HÀNH

7. Vào bên trong container web và xác nhận hostname bên trong khác với hostname của host.

Đáp án gợi ý
bash
hostname                         # trên host
docker container exec web hostname   # bên trong container

Hai giá trị khác nhau vì container có UTS namespace riêng.

THỰC HÀNH

8. Dọn sạch: dừng & xóa container web và cache, sau đó xóa image redis.

Đáp án gợi ý
bash
docker container stop web cache
docker container rm web cache
docker image rm redis

Phải stop trước khi rm (hoặc dùng rm -f). Không xóa được image nếu còn container tham chiếu.

THỬ THÁCH

9. Tự tái hiện thí nghiệm "bất biến": sửa nóng trang Nginx, xóa container, tạo lại từ cùng image và giải thích vì sao nội dung trở về mặc định. Nếu muốn nội dung được giữ lại sau khi xóa container thì hướng giải quyết là gì?

Đáp án gợi ý

Nội dung trở về mặc định vì thay đổi chỉ nằm ở lớp ghi (writable layer) của container, bị xóa cùng container; image nền không đổi. Muốn giữ lại: mount volume (vd -v /duong/dan/host:/usr/share/nginx/html) hoặc build image mới chứa nội dung đó qua Dockerfile. (Volume & Dockerfile là nội dung các Phần sau.)

THỬ THÁCH

10. Viết một vòng lặp bắn 100 request vào web, đồng thời quan sát docker stats và docker container logs -f. Mô tả bạn kỳ vọng thấy gì.

Đáp án gợi ý
bash
for i in $(seq 1 100); do curl -s "http://<ip-server>:8080/?n=$i" > /dev/null; done

Kỳ vọng: logs -f hiện thêm ~100 dòng access; docker stats thấy CPU%/MEM của web nhích lên trong lúc chạy tải rồi hạ về mức nghỉ. Gợi ý: có thể nhờ AI viết nhanh script tải nặng hơn (song song), nhưng luôn tự kiểm chứng kết quả.

Ghi nhớ Phần 1

10 điều cốt lõi

  • Container ra đời để tận dụng tài nguyên và chạy nhất quán trên mọi môi trường (ví von "container vận tải").
  • Container dùng chung kernel với host → nhẹ, nhanh, nhỏ hơn máy ảo; bản chất là một tiến trình được cô lập.
  • Kiến trúc Docker = daemon + registry + CLI; đường liền = pull, nét đứt = build.
  • Image gồm nhiều layer và các image chia sẻ layer → tiết kiệm dung lượng.
  • namespace + cgroups là nền tảng có sẵn trong Linux; Docker chỉ đóng gói dễ dùng.
  • Image là bất biến; muốn đổi lâu dài phải build image mới, không sửa nóng.
  • Container không lưu state — dữ liệu phải đưa ra volume, đừng nhồi hết vào container.
  • Phân biệt log container vs log ứng dụng; dùng logs -f, --tail để theo dõi.
  • docker stats / docker events để giám sát tài nguyên & sự kiện vòng đời.
  • Human in the Loop: mỗi bước phải có xác minh, kể cả khi dùng AI hỗ trợ.
